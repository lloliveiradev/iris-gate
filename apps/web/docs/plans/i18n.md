# Plan — Internationalization (en / es / pt)

> Goal: make every visible string in the web app translatable across English, Spanish, and Brazilian Portuguese, with proper Intl-based formatting for currency, dates, and numbers, plus a clean path to add locales later (mx-es, ar-es, en-GB, fr) without rewriting consumers.

---

## 0 · TL;DR

```
{t('payment_intents.title')}             // "Payment intents" | "Intenciones de pago" | "Intents de pagamento"
{t('payment_intents.create_cta')}        // "Create payment intent" | …
{t.rich('login.security_note', {…})}     // ICU-rich text with <code>, <link>
{format.dateTime(intent.created_at)}     // locale-aware
{format.currency(intent.amount.amount_cents / 100, 'BRL')}
```

- Library: **`next-intl`** (latest, Next 15 / App Router-native).
- Locale in URL: `/pt`, `/en`, `/es`. Default: `pt`.
- Catalogs: `apps/web/messages/{pt,en,es}.json` — typed via `next-intl`'s message-type pipeline.
- Currency / date / number: **Intl APIs**, not custom formatters — the existing `lib/format.ts` becomes locale-aware.

---

## 1 · Why next-intl

| Candidate                | Verdict                                                                                                                                                                                                         |
| ------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **next-intl**            | First-class App Router support, server + client components, type-safe messages, ICU MessageFormat, lazy locale loading, middleware-based locale negotiation. Most maintained Next-specific i18n. **Pick this.** |
| `react-i18next`          | Mature, framework-agnostic, but App Router setup is fiddly (must wrap server boundaries manually). Wins if we ever leave Next; until then, overkill.                                                            |
| `@lingui/core`           | Beautiful AST-extraction DX (`t``Hello {name}``), but heavier toolchain (Babel/SWC plugin) and weaker App Router story. Re-evaluate at scale.                                                                   |
| Custom `Intl` + JSON map | Avoid. Reinventing pluralization is a graveyard.                                                                                                                                                                |

Decision rationale: we're 100% Next.js for the foreseeable future, App Router-only, no SSR-incompatible legacy. next-intl is the natural fit.

## 2 · Locale strategy

### 2.1 · URL segment routing

```
/pt/dashboard/payment-intents   (default)
/en/dashboard/payment-intents
/es/dashboard/payment-intents
```

Pros: shareable URLs are explicit, SEO-friendly, deep links preserve language, easy to test with curl/Playwright.

Cons: every internal `<Link href="/dashboard">` becomes `<Link href={`/${locale}/dashboard`}>` — next-intl ships a localized `<Link>` that handles this.

Alternative (rejected): cookie-only with URL unchanged. Bad for sharing, bad for SSR cache keys.

### 2.2 · Locale detection

Middleware (`apps/web/src/middleware.ts`) resolves locale in this order:

1. URL prefix (highest priority — explicit user choice).
2. `NEXT_LOCALE` cookie (sticky from previous switch).
3. `Accept-Language` header (browser preference).
4. Fallback: `pt`.

next-intl's `createMiddleware()` does all of this; we configure `defaultLocale: 'pt'`, `locales: ['pt', 'en', 'es']`, `localeDetection: true`.

### 2.3 · Locale switcher

A `<LocaleSwitcher />` in the sidebar (right next to the `ThemeToggle`). On change:

1. Set `NEXT_LOCALE` cookie.
2. `router.replace` to the same pathname under the new locale prefix.

Languages render in their own names (`Português` / `English` / `Español`), not the current locale's names. Flag emoji is debatable (poor a11y, regional confusion) — recommend text only.

**Conventions:**

- **Namespace by surface** (`login.*`, `dashboard.payment_intents.*`), not by component name. Surfaces are stable; component trees aren't.
- **ICU MessageFormat** for pluralization (`{count, plural, …}`) and interpolation (`{merchantName}`). next-intl supports it natively.
- **Rich text** (with `<code>`, `<link>`, `<strong>`) via `t.rich()`. Tags are React-component-aware so we don't ship JSX in JSON.
- **No HTML in messages** outside the named-tag pattern — keeps catalogs translator-friendly and XSS-safe.
- **Status labels** live under `dashboard.payment_intents.statuses.*` (not the badge variant — the badge variant is style, not language). The `statusVariant()` helper stays in `lib/format.ts`; a separate `useStatusLabel(status)` hook reads the localized label.

`apps/web/messages/en.json`, `apps/web/messages/es.json` mirror the structure exactly. CI lints for missing keys (see §6).

## 4 · Wiring

### 4.1 · Install + config

```bash
yarn workspace @iris-gate/web add next-intl
```

`apps/web/src/i18n/config.ts`:

```ts
export const locales = ['pt', 'en', 'es'] as const;
export type Locale = (typeof locales)[number];
export const defaultLocale: Locale = 'pt';
```

`apps/web/src/i18n/request.ts` (server):

```ts
import { getRequestConfig } from 'next-intl/server';
import { locales, defaultLocale } from './config';

export default getRequestConfig(async ({ requestLocale }) => {
  const requested = await requestLocale;
  const locale = locales.includes(requested as never) ? requested! : defaultLocale;
  return {
    locale,
    messages: (await import(`../../messages/${locale}.json`)).default,
  };
});
```

### 4.2 · Middleware

`apps/web/src/middleware.ts`:

```ts
import createMiddleware from 'next-intl/middleware';
import { locales, defaultLocale } from './i18n/config';

export default createMiddleware({
  locales,
  defaultLocale,
  localeDetection: true,
  localePrefix: 'always', // /pt, /en, /es — always prefixed
});

export const config = {
  matcher: ['/((?!api|_next|_vercel|.*\\..*).*)'],
};
```

### 4.3 · Layout restructure

The current `apps/web/src/app/layout.tsx` becomes a thin shell. The localized layout moves to `apps/web/src/app/[locale]/layout.tsx`:

```
app/
├── layout.tsx               // <html>, font CSS vars, ThemeScript
├── globals.css
└── [locale]/
    ├── layout.tsx           // NextIntlClientProvider + dynamic locale
    ├── page.tsx             // landing (was /)
    ├── login/
    │   └── page.tsx         // (was /login)
    └── dashboard/
        ├── layout.tsx       // (was /dashboard/layout)
        ├── page.tsx
        └── payment-intents/
            └── …
```

Every existing route moves under `[locale]/`. Each internal link becomes either a localized `<Link>` from `next-intl/navigation` or accepts the current locale param.

### 4.4 · Component usage

**Server components** (the default in App Router):

```tsx
import { getTranslations } from 'next-intl/server';

export default async function Page() {
  const t = await getTranslations('dashboard.payment_intents');
  return <h1>{t('title')}</h1>;
}
```

**Client components**:

```tsx
'use client';
import { useTranslations } from 'next-intl';

export function NewIntentForm() {
  const t = useTranslations('dashboard.payment_intents.form');
  return <Button>{t('submit')}</Button>;
}
```

**Rich text** (`<code>`, `<strong>`, `<link>`):

```tsx
t.rich('login.description', {
  code: (chunks) => <code className="font-mono">{chunks}</code>,
});
```

## 5 · Formatting — currency, date, number

### 5.1 · Replace `lib/format.ts`

Today `formatMoney` and `formatDateTime` are hardcoded to `pt-BR`. Make them locale-aware via next-intl's formatter:

```ts
// server
import { getFormatter } from 'next-intl/server';

const f = await getFormatter();
f.number(intent.amount.amount_cents / 100, { style: 'currency', currency: intent.amount.currency });
f.dateTime(intent.created_at, { dateStyle: 'short', timeStyle: 'short' });

// client
import { useFormatter } from 'next-intl';
const f = useFormatter();
```

`next-intl` reads the locale from context — no need to pass it explicitly. Internally it calls `Intl.NumberFormat` / `Intl.DateTimeFormat`.

### 5.2 · Currency consistency

Money lives in **centavos** in the API; division by 100 happens in the formatter call. The currency code (`BRL`, `USD`, `MXN`, etc.) is **always** what comes from the server — we do not infer currency from locale. A merchant in Brazil may receive a USD-denominated intent; the locale only changes how it's displayed (`R$ 1.990,00` in pt vs `BRL 1,990.00` in en).

### 5.3 · Relative time

For "criado há 3 minutos" timestamps in lists, use `f.relativeTime(date)` — Intl-backed, locale-aware. Falls back to absolute date past 24h.

## 6 · DX guardrails

### 6.1 · Type-safe message keys

`apps/web/src/i18n/types.d.ts`:

```ts
type Messages = typeof import('../../messages/pt.json');
declare interface IntlMessages extends Messages {}
```

This gives autocomplete + compile-time errors on missing keys in `t('…')` calls (next-intl built-in).

### 6.2 · Missing-key lint

A small Vitest task (or a tsx script) that:

1. Loads `pt.json` (source of truth).
2. Loads `en.json` and `es.json`.
3. Diffs keysets, errors on missing keys in any non-default locale.

Wire it into the existing CI step. Tab-completion + this lint = no shipped untranslated strings.

### 6.3 · Translation workflow

V1: hand-translate in the JSON files. V2 (when needed): integrate with Crowdin / Lokalise / Tolgee — all support next-intl message JSON natively.

Avoid auto-translating with an LLM at build time. Status labels and CTA verbs are too consequential.

## 7 · API + backend coordination

### 7.1 · Localized errors from the API

The Go API returns `problem+json` with an English `detail`. Options:

- **A** — keep `detail` English; web maps known error codes to translated messages via the `errors.*` namespace. **Recommended.** Backend stays simple; front-end controls the user-facing copy.
- **B** — API reads `Accept-Language` and localizes `detail`. Adds backend complexity; useful when the API is consumed by third-party integrators, but that's not the case for the merchant dashboard.

Decision: A. Add an `errors.api.{code}` namespace per known error code (`payment_intent.not_found`, `idempotency_key.conflict`, etc.) and translate.

### 7.2 · Currency formatting on the server

Server actions don't render strings to the user; they return data. Formatting is always client- or layout-side. No backend changes needed.

## 8 · Phased rollout

**Phase 1 — Plumbing** (single PR)
- Install `next-intl`, add config + middleware.
- Move every route under `[locale]/`.
- Wire the layout provider.
- Migrate **one surface end-to-end** (recommend `/login` — small, contained) to prove the loop.
- `pt.json` populated; `en.json` and `es.json` cloned with placeholders + lint catching the gap.

**Phase 2 — Surface migration** (per-PR)
- Landing page (`Hero`, `FeatureRow`, `CTA`, `Testimonial`, `SiteHeader`, `SiteFooter`).
- Dashboard overview + payment-intents list + detail + new-intent form.
- Each PR translates pt + en; es trails by one PR.

**Phase 3 — Polish**
- `LocaleSwitcher` component, sidebar placement.
- Localized `lib/format.ts` (`formatMoney` / `formatDateTime` rewritten on top of `useFormatter`).
- Relative-time helper.
- Translation completeness CI check.

**Phase 4 — Extend** (when needed)
- New locales (mx-es differences, en-GB, fr) — add to `locales` array, drop `messages/<code>.json`, run the lint, ship.
- Integrate with a TMS if translation volume warrants it.

## 9 · Open questions

1. **Default locale on first visit** — auto-detect from `Accept-Language` (current plan), or always start in `pt` regardless? Auto-detect is more welcoming; `pt`-default is more predictable. Recommend auto-detect with a one-time cookie save on first manual switch.
2. **Locale in dashboard breadcrumb / browser title** — `<title>IrisGate · Payment intents</title>` should localize. next-intl supports `generateMetadata` with `getTranslations`. Easy; just remember in Phase 2.
3. **Numbers in API responses (e.g., `amount_cents`)** — never reformat at the boundary, only at render. The integer stays an integer all the way through; we don't ship `R$ 1.990,00` strings over the wire.
4. **RTL** — not a current requirement. If Arabic/Hebrew lands later, the design system needs an audit (logical properties already used in most places; flex/grid is RTL-friendly; the dark brand panel on login may need a mirrored gradient origin).
5. **Marketing site SEO** — `<html lang>` should reflect the locale. next-intl wires this in the localized `[locale]/layout.tsx`. Also add `<link rel="alternate" hreflang>` for each locale on the landing page (small `hreflang` helper or hard-code in metadata).
