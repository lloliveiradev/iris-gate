# Zod 4 Schema Examples

All examples follow the canonical pattern:

1. **DTO types stay in `types/`** (owned by the `django-to-typescript` skill). Always
   read the DTO before writing the schema.
2. Schema is the runtime validator only — `Schema` suffix on the variable.
3. No `satisfies z.ZodType<…>` and no `: z.ZodType<X>` annotations.
4. **No `z.infer` / `z.input` / `z.output` exports from the schema file.**
   Use them inline at the consuming code if needed.
5. Booleans use `z.boolean()` for JSON/RHF and `z.stringbool()` for raw
   form/URL/env strings — `z.coerce.boolean()` is banned.

---

## Example 1 — Simple Entity (Article)

### DTO (read first — `types/article-types.ts`, generated by `django-to-typescript`)

```ts
// types/article-types.ts
export type CreateArticleDTO = {
  title: string;
  body: string;
  status?: "draft" | "published";
  author: number;
};

export type UpdateArticleDTO = Partial<CreateArticleDTO>;
```

### Schema

```ts
// schemas/article-schema.ts
import { z } from "zod";

export const CreateArticleSchema = z.object({
  title: z.string().min(1),
  body: z.string().min(1),
  status: z.enum(["draft", "published"]).optional(),
  author: z.number().int().positive(),
});

export const UpdateArticleSchema = CreateArticleSchema.partial();
```

```ts
// schemas/index.ts
export { CreateArticleSchema, UpdateArticleSchema } from "./article-schema";
```

### Consumer

```ts
import type { CreateArticleDTO } from "../types";
import { CreateArticleSchema } from "../schemas";

async function create(data: CreateArticleDTO) {
  const validated = CreateArticleSchema.safeParse(data);
  // …
}
```

## Example 2 — Numeric Union with Documented Choices (Order)

Mirrors a Django `IntegerChoices`. Use `z.literal([…])` (Zod 4 multi-literal)
instead of stacking `z.union([z.literal(1), …])`.

### DTO

```ts
// types/order-types.ts
export type OrderStatus = 1 | 2 | 3 | 4 | 5;
// 1 = Pending | 2 = Processing | 3 = Shipped | 4 = Delivered | 5 = Cancelled

export type CreateOrderDTO = {
  customer: number;
  status?: OrderStatus;
  total: number;
  notes?: string | null;
};

export type UpdateOrderDTO = Partial<CreateOrderDTO>;
```

### Schema

```ts
// schemas/order-schema.ts
import { z } from "zod";

/** Mirrors OrderStatus — 1=Pending | 2=Processing | 3=Shipped | 4=Delivered | 5=Cancelled */
const OrderStatusSchema = z.literal([1, 2, 3, 4, 5]);

export const CreateOrderSchema = z.object({
  customer: z.number().int().positive(),
  status: OrderStatusSchema.optional(),
  total: z.number().positive(),
  notes: z.string().nullish(),
});

export const UpdateOrderSchema = CreateOrderSchema.partial();
```

## Example 3 — Nullable & Optional Fields (User)

```ts
// types/user-types.ts
export type CreateUserDTO = {
  email: string;
  username: string;
  password: string;
  bio?: string | null;
  avatar?: string | null;
};
```

```ts
// schemas/user-schema.ts
import { z } from "zod";

export const CreateUserSchema = z.object({
  email: z.email(),
  username: z.string().min(1).max(150),
  password: z.string().min(8),
  bio: z.string().nullish(), // optional AND nullable → .nullish()
  avatar: z.url().nullish(),
});

export const UpdateUserSchema = CreateUserSchema.partial();
```

## Example 4 — `Update = Partial<Create> & { id }`

When the DTO type extends `Partial` with a required `id` (so consumers can read
it back from the validated payload to build the PATCH URL), use
`.partial().extend({ … })`.

### DTO

```ts
// types/article-types.ts
export type UpdateArticleDTO = Partial<CreateArticleDTO> & { id: string };
```

### Schema

```ts
// schemas/article-schema.ts
export const UpdateArticleSchema = CreateArticleSchema.partial().extend({
  id: z.uuid(),
});
```

## Example 5 — URL / Form Schema with `z.stringbool()` and Coerce

A separate schema for URL or `FormData` parsing. Strings are coerced to numbers
and **boolish strings** go through `z.stringbool()`. Input ≠ output here, so
consumers use `z.input` / `z.output` **inline at the call-site**.

### Schema

```ts
// schemas/order-search-schema.ts
import { z } from "zod";

/**
 * Used with nuqs / raw FormData — input arrives as strings.
 * Numbers/dates: z.coerce.* | Booleans: z.stringbool() (NEVER z.coerce.boolean)
 */
export const OrderSearchSchema = z.object({
  customer: z.coerce.number().int().positive(),
  status: z.coerce
    .number()
    .pipe(z.literal([1, 2, 3, 4, 5]))
    .optional(),
  total_min: z.coerce.number().positive().optional(),
  created_after: z.iso.datetime({ offset: true }).optional(),
  is_active: z.stringbool().optional(), // "true"/"1"/"on"/"yes" → true
});
```

### Consumer (form values type inline)

```ts
import { OrderSearchSchema } from "../schemas";

type FormValues = z.input<typeof OrderSearchSchema>; // strings (form raw)
type SubmitPayload = z.output<typeof OrderSearchSchema>; // parsed types
```

> `is_active: z.coerce.boolean()` would map `"false"` → `true` because of native
> `Boolean()`. Always use `z.stringbool()` here.

## Example 6 — JSONField (`Record<string, unknown>`)

```ts
// types/config-types.ts
export type CreateConfigDTO = {
  name: string;
  metadata: Record<string, unknown>;
  raw_payload?: unknown;
};
```

```ts
// schemas/config-schema.ts
import { z } from "zod";

export const CreateConfigSchema = z.object({
  name: z.string().min(1),
  metadata: z.record(z.string(), z.unknown()),
  raw_payload: z.unknown().optional(),
});

export const UpdateConfigSchema = CreateConfigSchema.partial();
```

## Example 7 — Discriminated Union (Schedule)

Canonical example for type-dependent config fields. Shared fields are extracted
into `ScheduleBase` and each arm extends it.

### DTO

```ts
// types/schedule-types.ts
export type ScheduleType = 1 | 2 | 3 | 4;
// 1 = Cron | 2 = Interval | 3 = Recurring | 4 = One Time

export type CreateScheduleDTO = {
  name: string;
  description?: string | null;
  is_active?: boolean;
  schedule_type: ScheduleType;
  schedule_config: Record<string, unknown>; // shape varies by schedule_type
};
```

### Step 1 — confirm config shapes

Before generating, ask:

> "The `schedule_config` field shape varies per `schedule_type`. Could you share
> the config structure for each type (Cron, Interval, Recurring, One Time)?
> I'll use `z.discriminatedUnion()` to type each arm correctly."

### Schema

```ts
// schemas/schedule-schema.ts
import { z } from "zod";

// shared fields
const ScheduleBase = z.object({
  name: z.string().min(1),
  description: z.string().nullish(),
  is_active: z.boolean().optional(),
});

// config sub-schemas (one per schedule_type arm)
const CronConfigSchema = z.object({ cron: z.string().min(1) });
const IntervalConfigSchema = z.object({
  unit: z.enum(["minutes", "hours", "days"]),
  value: z.number().int().positive(),
});
const RecurringConfigSchema = z.object({
  frequency: z.enum(["daily", "weekly", "monthly"]),
  days_of_week: z.array(z.number().int().min(0).max(6)).optional(),
  start_time: z.string().regex(/^\d{2}:\d{2}$/),
  end_time: z
    .string()
    .regex(/^\d{2}:\d{2}$/)
    .optional(),
});
const OneTimeConfigSchema = z.object({
  start_datetime: z.iso.datetime({ offset: true }),
  end_datetime: z.iso.datetime({ offset: true }).optional(),
});

// Create — discriminated union on schedule_type
export const CreateScheduleSchema = z.discriminatedUnion("schedule_type", [
  ScheduleBase.extend({
    schedule_type: z.literal(1),
    schedule_config: CronConfigSchema,
  }),
  ScheduleBase.extend({
    schedule_type: z.literal(2),
    schedule_config: IntervalConfigSchema,
  }),
  ScheduleBase.extend({
    schedule_type: z.literal(3),
    schedule_config: RecurringConfigSchema,
  }),
  ScheduleBase.extend({
    schedule_type: z.literal(4),
    schedule_config: OneTimeConfigSchema,
  }),
]);

// Update — rebuild union per arm; .partial() does not work on discriminatedUnion
const ScheduleBasePartial = ScheduleBase.partial();
export const UpdateScheduleSchema = z.discriminatedUnion("schedule_type", [
  ScheduleBasePartial.extend({
    schedule_type: z.literal(1),
    schedule_config: CronConfigSchema.partial().optional(),
  }),
  ScheduleBasePartial.extend({
    schedule_type: z.literal(2),
    schedule_config: IntervalConfigSchema.partial().optional(),
  }),
  ScheduleBasePartial.extend({
    schedule_type: z.literal(3),
    schedule_config: RecurringConfigSchema.partial().optional(),
  }),
  ScheduleBasePartial.extend({
    schedule_type: z.literal(4),
    schedule_config: OneTimeConfigSchema.partial().optional(),
  }),
]);
```

```ts
// schemas/index.ts
export { CreateScheduleSchema, UpdateScheduleSchema } from "./schedule-schema";
```

### Runtime narrowing after parse

```ts
import { CreateScheduleSchema } from "../schemas";

const result = CreateScheduleSchema.parse(input);

if (result.schedule_type === 1) {
  result.schedule_config.cron; // typed as CronConfig
}
```

## Example 8 — Shared Field Schemas

Reuse common field shapes via a private `shared-schemas.ts` (not re-exported
from the barrel).

```ts
// schemas/shared-schemas.ts
import { z } from "zod";

export const idField = z.uuid();
export const isoDateField = z.iso.datetime({ offset: true });
export const nullableText = z.string().nullable();
export const positiveInt = z.number().int().positive();
export const slugField = z.string().regex(/^[-a-zA-Z0-9_]+$/);
```

```ts
// schemas/article-schema.ts
import { z } from "zod";
import { positiveInt, nullableText } from "./shared-schemas";

export const CreateArticleSchema = z.object({
  title: z.string().min(1),
  body: nullableText,
  author: positiveInt,
});

export const UpdateArticleSchema = CreateArticleSchema.partial();
```

```ts
// schemas/index.ts
export { CreateArticleSchema, UpdateArticleSchema } from "./article-schema";
// shared-schemas is internal — do not re-export
```
